# AGENTS.md

Инструкции для AI-агентов и разработчиков, работающих с проектом **babylon-snake-js** — игра «Змейка» на Babylon.js.

## Обязательные правила задания

1. **Сборщик** — локальный проект на **Vite** (Webpack допустим, но не смешивать).
2. **Язык** — только **TypeScript** в режиме `strict`. Использовать доступные типы (включая типы Babylon.js) и ООП.
3. **GitHub** — у задачи есть отдельный репозиторий; каждая фича пушится по мере готовности, а не одним коммитом в конце.
4. **Никаких лишних аллокаций** (особенно в коде, который выполняется каждый кадр), **никакого дублирования кода**, **никаких god-классов и god-методов**.

Нарушение любого из этих пунктов считается ошибкой, даже если код работает.

## Стек и команды

- Vite + TypeScript + `@babylonjs/core`
- GUI: `@babylonjs/gui` (версия совпадает с `@babylonjs/core`)
- Физика: Havok (`@babylonjs/havok`) через Physics V2 API — `HavokPlugin`, `PhysicsAggregate` / `PhysicsBody`, `PhysicsConstraint`
- Менеджер пакетов: `npm`

Babylon.js 9 разделён на `*.pure` модули и модули с побочными эффектами. Если метод сцены «не существует» (например, `scene.enablePhysics`), значит, не подключён модуль, который его регистрирует (`@babylonjs/core/Physics/joinedPhysicsEngineComponent`). Havok WASM подключается через `?url` и исключён из `optimizeDeps` в [vite.config.ts](vite.config.ts).

```bash
npm install       # установка зависимостей
npm run dev       # dev-сервер
npm run build     # tsc --noEmit && vite build
npm run preview   # просмотр production-сборки
```

Перед каждым коммитом `npm run build` должен проходить без ошибок и предупреждений типов.

## TypeScript

- `tsconfig.json`: `"strict": true`, `"noUnusedLocals": true`, `"noUnusedParameters": true`, `"noImplicitReturns": true`, `"noFallthroughCasesInSwitch": true`, `"verbatimModuleSyntax": true` (импорты только типов — через `import type`).
- Запрещены `any`, `@ts-ignore` и `as unknown as` без письменного обоснования в комментарии.
- Явно указывать типы публичных методов и полей; модификаторы доступа (`private`, `protected`, `public`, `readonly`) ставить всегда.
- Для фиксированных наборов значений (направления, состояния игры) — `enum` или union-типы, а не «магические» строки и числа.
- Импорт из Babylon.js — точечный (`import { Vector3 } from "@babylonjs/core/Maths/math.vector"`), чтобы работал tree-shaking.

## ООП и архитектура

- **Один класс — одна ответственность.** Если описание класса требует слова «и», его стоит разделить.
- Ориентиры по размеру: класс — до ~200 строк, метод — до ~30 строк. Превышение — повод выделить класс или метод.
- Зависимости передаются через конструктор (composition over inheritance); глобальных синглтонов и мутабельного глобального состояния избегать.
- Змейка физическая: её состояние — это физические тела Havok, поэтому сущность владеет мешем и телом, а создание тел, соединений и материалов вынесено в отдельные классы.
- Общие контракты описываются интерфейсами (например, `SnakeSegmentMetadata`).
- Константы (размеры, массы, цвета, гравитация) — только в [src/core/GameConfig.ts](src/core/GameConfig.ts), а не разбросаны по коду.
- Каждый меш сегмента хранит типизированный объект в `mesh.metadata` (минимум `id`).

### Физика и ввод

- Коллизии задаются только через [CollisionFilter.ts](src/physics/CollisionFilter.ts): сегменты змейки сталкиваются только с полом; осколки — с полом и друг с другом. Новой сущности нужна своя группа в `CollisionGroup`.
- Код ввода не трогает физическое тело напрямую, а вызывает методы сущностей (`SnakeSegment.beginManualControl`, `Snake.setFollowersCrawling`, `Snake.releaseToPhysics`).
- Змейка должна двигаться ровно: сегменты не перекручиваются и не складываются. За это отвечают 6DoF-соединения (сдвиг и кручение заблокированы, изгиб ограничен `maxBendAngle` / `maxPitchAngle`, мотор выпрямляет), демпфирование и перетаскивание в горизонтальной плоскости. Не заменять их на `BallAndSocketConstraint`.
- **Ловушка Babylon 9:** `disablePreStep` — не отдельный флаг, а сокращение для типа pre-step (`true` = `DISABLED`, `false` = `TELEPORT`). `setPrestepType(ACTION)` тоже включает pre-step. Тело с включённым pre-step физика каждый шаг тянет к трансформу меша — оно зависает в воздухе. Поэтому по умолчанию pre-step у всех тел выключен.
- **Змейка ползёт как змея — не ломать.** При перетаскивании по полу ведущий сегмент получает `disablePreStep = false` (TELEPORT за курсором), а остальные — pre-step `ACTION` (`followWithoutInertia`): каждый шаг им задаётся скорость к собственному трансформу, что гасит инерцию и гравитацию, и двигают их только соединения. Тело идёт по следу головы без заноса.
- В режиме подъёма (Shift) остальные сегменты под обычной физикой (`releaseToPhysics`), чтобы змейка провисала и падала. Переключение Shift во время перетаскивания сразу меняет режим.
- После отпускания все сегменты возвращаются под обычную физику (`disablePreStep = true`) со сброшенной скоростью. Нельзя оставлять pre-step включённым после перетаскивания — змейка зависнет в воздухе и не сможет упасть и разбиться.
- Телепорт тела (`PhysicsBoxEntity.teleportToMesh`) — временно `disablePreStep = false` и `HavokPlugin.setPhysicsBodyTransformation`.
- Выключенные тела не удаляются из мира Havok (иначе теряются подписки на столкновения): `PhysicsBoxEntity.deactivate` делает тело `STATIC`, обнуляет маски коллизий и скрывает меш.
- Параметры плавности и разрушения (`linearDamping`, `angularDamping`, `joint.*`, `destruction.*`) настраиваются только в конфиге. Порог `impactImpulseThreshold` подобран так, что перетаскивание по полу даёт импульсы ~0.4, а падение с высоты 3–5 м — 4–9.

### Разрушение

- Любой источник разрушения (удар о землю, луч) вызывает только `SegmentShatterer.shatter(index)` — не дублировать логику подмены.
- Индекс сегмента по телу — `Snake.indexOfBody`.

- Осколки и их тела создаются заранее в `ShatteredSegmentPool`; во время игры ничего не создаётся.
- Столкновения ловятся через `body.getCollisionObservable()` (нужен `setCollisionCallbackEnabled(true)`). Колбэк вызывается посреди обработки шага Havok, поэтому в нём сегмент только помечается, а подмена выполняется в `scene.onAfterPhysicsObservable`.
- Скорость разлёта осколков задаётся в м/с и умножается на массу осколка, чтобы импульс не зависел от размера сетки осколков.

## Производительность: без аллокаций в горячем пути

Горячий путь — всё, что вызывается каждый кадр или тик: `onBeforeRenderObservable`, `update()`, обработка движения, проверка столкновений.

**Запрещено в горячем пути:**
- `new Vector3(...)`, `new Color3(...)`, `new Quaternion(...)` и другие `new` для временных значений;
- методы Babylon.js, которые возвращают новый объект (`add`, `subtract`, `scale`, `clone` …), вместо них — `*ToRef` / `*InPlace` (`addToRef`, `scaleInPlace`, `copyFrom`);
- литералы объектов и массивов (`{ x, y }`, `[a, b]`), `map` / `filter` / `reduce` / `slice` / `concat`, spread;
- замыкания и стрелочные функции, создаваемые на каждый вызов;
- конкатенация и шаблонные строки (например, обновление текста счёта каждый кадр — только при изменении значения);
- создание и удаление мешей (`MeshBuilder.Create*`, `dispose`) при движении змейки или появлении еды.

**Как делать:**
- временные векторы — `private readonly` поля класса или модульные scratch-переменные, переиспользуемые между вызовами;
- сегменты змейки и еда — **пул объектов** (или `InstancedMesh` / thin instances), меши создаются заранее и переиспользуются;
- тело змейки — кольцевой буфер или массив фиксированной вместимости с индексами, а не `unshift` / `pop` с перераспределением памяти;
- поле — плоский типизированный массив (`Uint8Array`) для проверки занятости клеток за O(1);
- материалы создаются один раз и разделяются между мешами;
- обработчики событий и колбэки создаются один раз (в конструкторе) и отписываются в `dispose()`.

## Без дублирования

- Повторяющаяся логика (перевод клетки в мировые координаты, проверка границ, создание материала) — в одном месте.
- Перед написанием нового хелпера проверить, нет ли уже подходящего в `utils/` или в самом Babylon.js.
- Похожие view-классы выносят общее в базовый класс или композицию, а не копируют код.

## Жизненный цикл ресурсов

- Каждый класс, который владеет мешами, материалами, observers или DOM-слушателями, реализует `dispose()` и освобождает всё, что создал.
- Перезапуск игры не должен приводить к утечкам: состояние сбрасывается через `reset()`, а не через пересоздание сцены.

### Полоса препятствий и финиш

- Трасса задаётся в `gameConfig.course`: слалом из неподвижных лучей от краёв арены (проходы попеременно справа и слева) и качающийся луч, который доходит до обоих краёв, поэтому безопасной полосы у края нет. Змейка стартует у ближнего края, финиш — у дальнего.
- Лучи — физический `HavokPlugin.raycast` с `collideWith: CollisionGroup.SnakeSegment` и одним переиспользуемым `PhysicsRaycastResult`; проверка и движение лучей — в `onAfterPhysicsObservable`, без аллокаций. `Ray` хранит ссылку на вектор начала, поэтому `RayHelper` сам следует за качающимся лучом.
- Финиш — статичное тело с `shape.isTrigger = true` и группой `FinishZone`; маска сегментов змейки включает `FinishZone`. Событие приходит из `onTriggerCollisionObservable` посреди шага, поэтому колбэк финиша вызывается после шага и только один раз; он открывает `VictoryPanel` (не `alert`). Меш финиша `isPickable = false`, чтобы не мешать перетаскиванию.

### Пыль

- Системы частиц создаются только в `DustParticlePool` при старте; во время игры — `emit(position, burst)`. Система свободна, когда `isStarted()` вернул `false` (после `targetStopDuration` и догорания частиц). Если свободных нет, выброс пропускается — новые системы не создаются.
- Текстура `RocketSmokeAlpha.png` загружается один раз и разделяется всеми системами (`dispose(false)` у систем, текстура освобождается отдельно).
- Позиция пыли от контакта — `event.point` из события столкновения. Чтобы не запускать систему на каждом шаге физики, облачко появляется при начале контакта с импульсом не меньше `landingImpulseThreshold` или после того, как сегмент проползёт `travelDistancePerPuff` метров.
- При разрушении `SegmentShatterer` выбрасывает пресет `dust.destruction` в центре сегмента.
- `setCollisionCallbackEnabled(true)` включается один раз в конструкторе `SnakeSegment`: столкновения слушают несколько систем, и ни одна не должна выключать их другой.
- Размер пула подобран так, чтобы при быстром ползании (~12 систем) оставался запас на облака разрушения.

### GUI

- Весь экранный интерфейс — `@babylonjs/gui` на одном полноэкранном `AdvancedDynamicTexture` в `GameUi`; браузерные `alert`/`confirm` не использовать.
- Панели ставят `isPointerBlocker = true` (через `GuiStyle.createPanel`), чтобы клики по кнопкам не выбирали меши и не вращали камеру.
- Выбор меша — `MeshSelector` по `POINTERDOWN` и `isMeshMetadata(mesh.metadata)`; клик по мешу без id не сбрасывает выбор. Поле показывает `metadata.id`.
- Кнопка цвета назначает выбранному мешу материал из `SelectableColor`: `RunningGradientMaterial`, если отмечен чекбокс «Градиент», иначе однотонный `StandardMaterial` того же цвета. Оба варианта создаются один раз при сборке панели. Переключение чекбокса сразу меняет вариант у выбранного меша, если он перекрашен кнопкой. Не менять цвет общих материалов змейки — перекрасятся все сегменты. Осколки берут материал сегмента, поэтому сохраняют выбранный цвет.
- Тексты и цвета GUI — в `gameConfig.ui`; оформление — только через `GuiStyle`.

### Шейдерные материалы

- Собственные материалы наследуют `ShaderMaterial`; GLSL лежит в `src/materials/shaders/*.glsl` и передаётся как `{ vertexSource, fragmentSource }` через импорт `?raw` — без глобального `Effect.ShadersStore`.
- Все используемые uniform перечисляются в `uniforms` при создании материала. Анимируемый uniform `time` обновляется в `scene.onBeforeRenderObservable` через `setFloat` — без аллокаций; подписка снимается в переопределённом `dispose`.
- Параметры эффекта (`speed`, `stripeFrequency`) — в `gameConfig.ui.colorEffect`.
