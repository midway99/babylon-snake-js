# AGENTS.md

Инструкции для AI-агентов и разработчиков, работающих с проектом **babylon-snake-js** — игра «Змейка» на Babylon.js.

## Обязательные правила задания

1. **Сборщик** — локальный проект на **Vite** (Webpack допустим, но не смешивать).
2. **Язык** — только **TypeScript** в режиме `strict`. Использовать доступные типы (включая типы Babylon.js) и ООП.
3. **GitHub** — у задачи есть отдельный репозиторий; каждая фича пушится по мере готовности, а не одним коммитом в конце.
4. **Никаких лишних аллокаций** (особенно в коде, который выполняется каждый кадр), **никакого дублирования кода**, **никаких god-классов и god-методов**.

Нарушение любого из этих пунктов считается ошибкой, даже если код работает.

## Стек и команды

- Vite + TypeScript + `@babylonjs/core`
- Физика: Havok (`@babylonjs/havok`) через Physics V2 API — `HavokPlugin`, `PhysicsAggregate` / `PhysicsBody`, `PhysicsConstraint`
- Менеджер пакетов: `npm`

Babylon.js 9 разделён на `*.pure` модули и модули с побочными эффектами. Если метод сцены «не существует» (например, `scene.enablePhysics`), значит, не подключён модуль, который его регистрирует (`@babylonjs/core/Physics/joinedPhysicsEngineComponent`). Havok WASM подключается через `?url` и исключён из `optimizeDeps` в [vite.config.ts](vite.config.ts).

```bash
npm install       # установка зависимостей
npm run dev       # dev-сервер
npm run build     # tsc --noEmit && vite build
npm run preview   # просмотр production-сборки
```

Перед каждым коммитом `npm run build` должен проходить без ошибок и предупреждений типов.

## TypeScript

- `tsconfig.json`: `"strict": true`, `"noUnusedLocals": true`, `"noUnusedParameters": true`, `"noImplicitReturns": true`, `"noFallthroughCasesInSwitch": true`, `"verbatimModuleSyntax": true` (импорты только типов — через `import type`).
- Запрещены `any`, `@ts-ignore` и `as unknown as` без письменного обоснования в комментарии.
- Явно указывать типы публичных методов и полей; модификаторы доступа (`private`, `protected`, `public`, `readonly`) ставить всегда.
- Для фиксированных наборов значений (направления, состояния игры) — `enum` или union-типы, а не «магические» строки и числа.
- Импорт из Babylon.js — точечный (`import { Vector3 } from "@babylonjs/core/Maths/math.vector"`), чтобы работал tree-shaking.

## ООП и архитектура

- **Один класс — одна ответственность.** Если описание класса требует слова «и», его стоит разделить.
- Ориентиры по размеру: класс — до ~200 строк, метод — до ~30 строк. Превышение — повод выделить класс или метод.
- Зависимости передаются через конструктор (composition over inheritance); глобальных синглтонов и мутабельного глобального состояния избегать.
- Змейка физическая: её состояние — это физические тела Havok, поэтому сущность владеет мешем и телом, а создание тел, соединений и материалов вынесено в отдельные классы.
- Общие контракты описываются интерфейсами (например, `SnakeSegmentMetadata`).
- Константы (размеры, массы, цвета, гравитация) — только в [src/core/GameConfig.ts](src/core/GameConfig.ts), а не разбросаны по коду.
- Каждый меш сегмента хранит типизированный объект в `mesh.metadata` (минимум `id`).

Структура (дополняется по мере развития):

```
src/
  main.ts                      # точка входа: только создание Game и запуск
  core/
    Game.ts                    # движок, сцена, рендер-цикл, владение сущностями
    GameConfig.ts              # типизированный конфиг и его значения
  input/
    SnakeDragController.ts     # вешает перетаскивание на каждый сегмент
    SegmentDragHandler.ts      # PointerDragBehavior + onDragStart/onDragEnd
  physics/
    HavokPhysicsLoader.ts      # загрузка Havok WASM и scene.enablePhysics
    CollisionFilter.ts         # группы и маски коллизий (filterMembershipMask / filterCollideMask)
  scene/
    Arena.ts                   # камера, свет, пол со статичным телом
  snake/
    Snake.ts                   # сборка змейки из сегментов и соединений
    SnakeSegment.ts            # меш-параллелепипед + PhysicsAggregate (BOX) + metadata
    SnakeSegmentMetadata.ts    # тип объекта в mesh.metadata
    SegmentConnector.ts        # BallAndSocketConstraint между соседними сегментами
    SnakeMaterials.ts          # общие StandardMaterial головы и тела
```

Будущие модули (еда, UI, пулы объектов) кладутся в отдельные папки: `food/`, `ui/`, `utils/`.

### Физика и ввод

- Коллизии задаются только через [CollisionFilter.ts](src/physics/CollisionFilter.ts): сегменты змейки сталкиваются с полом, но не друг с другом. Новой сущности нужна своя группа в `CollisionGroup`.
- Код ввода не трогает физическое тело напрямую, а вызывает методы сущности (`SnakeSegment.beginManualControl` / `endManualControl`).
- Перетаскиваемое тело на время drag: `disablePreStep = false` и тип движения `ANIMATED` (физика читает позицию из трансформа, гравитация и соединения его не сдвигают). После drag: `disablePreStep = true`, `DYNAMIC`, линейная и угловая скорость обнуляются.

## Производительность: без аллокаций в горячем пути

Горячий путь — всё, что вызывается каждый кадр или тик: `onBeforeRenderObservable`, `update()`, обработка движения, проверка столкновений.

**Запрещено в горячем пути:**
- `new Vector3(...)`, `new Color3(...)`, `new Quaternion(...)` и другие `new` для временных значений;
- методы Babylon.js, которые возвращают новый объект (`add`, `subtract`, `scale`, `clone` …), вместо них — `*ToRef` / `*InPlace` (`addToRef`, `scaleInPlace`, `copyFrom`);
- литералы объектов и массивов (`{ x, y }`, `[a, b]`), `map` / `filter` / `reduce` / `slice` / `concat`, spread;
- замыкания и стрелочные функции, создаваемые на каждый вызов;
- конкатенация и шаблонные строки (например, обновление текста счёта каждый кадр — только при изменении значения);
- создание и удаление мешей (`MeshBuilder.Create*`, `dispose`) при движении змейки или появлении еды.

**Как делать:**
- временные векторы — `private readonly` поля класса или модульные scratch-переменные, переиспользуемые между вызовами;
- сегменты змейки и еда — **пул объектов** (или `InstancedMesh` / thin instances), меши создаются заранее и переиспользуются;
- тело змейки — кольцевой буфер или массив фиксированной вместимости с индексами, а не `unshift` / `pop` с перераспределением памяти;
- поле — плоский типизированный массив (`Uint8Array`) для проверки занятости клеток за O(1);
- материалы создаются один раз и разделяются между мешами;
- обработчики событий и колбэки создаются один раз (в конструкторе) и отписываются в `dispose()`.

## Без дублирования

- Повторяющаяся логика (перевод клетки в мировые координаты, проверка границ, создание материала) — в одном месте.
- Перед написанием нового хелпера проверить, нет ли уже подходящего в `utils/` или в самом Babylon.js.
- Похожие view-классы выносят общее в базовый класс или композицию, а не копируют код.

## Жизненный цикл ресурсов

- Каждый класс, который владеет мешами, материалами, observers или DOM-слушателями, реализует `dispose()` и освобождает всё, что создал.
- Перезапуск игры не должен приводить к утечкам: состояние сбрасывается через `reset()`, а не через пересоздание сцены.

## Git и GitHub

- Одна фича — один логически завершённый коммит (или короткая серия), затем push. Не копить изменения.
- Сообщения коммитов на английском, в стиле Conventional Commits:
  `feat: add snake movement`, `fix: prevent reverse direction`, `refactor: extract SnakeView`, `chore: setup vite`.
- В репозиторий не попадают `node_modules/`, `dist/`, `.env`, файлы IDE — всё это в `.gitignore`.
- Прямой push в `main` допустим только для этой учебной задачи; перед push сборка должна проходить.
